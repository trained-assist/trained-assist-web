# Этап C — проверяемый деплой и реальный browser smoke

Эпик: https://github.com/trained-assist/trained-assist-web/issues/35
Этап A: https://github.com/trained-assist/trained-assist-web/pull/36
Этап B: https://github.com/trained-assist/trained-assist-web/pull/37

Статус: только постановка. В этом коммите нет изменений workflow, инфраструктуры или приложения. Деплой, тестовые live-сессии и разработка не запускаются этой постановкой.

## Результат

Известно, каким способом публикуется приложение, какой git SHA находится на проверенном URL и прошёл ли именно этот build сценарий login → New → проект → create → refresh → reply → ответ. Пользователь получает работающий проверенный сценарий, а не только зелёный mock-тест.

Этап зависит от проверенных реализаций A и B. Аудит существующего CD можно делать заранее. Рабочая область: `.github/workflows/`, `package.json` и lockfile при необходимости, тестовый smoke runner/config, документация деплоя и `docs/ACCEPTANCE-TESTS.md`. Не переделывать UI или session-store. `wrangler.toml` менять только после проверки реального механизма выкладки.

## 1. Аудит без догадок

При подготовке эпика `check` запускал `npm test`, а `staging-gate` — `npm run test:staging`, который снова запускал `npm test`. Это две проверки, не доказательство тестирования deployed окружения. Перед реализацией повторно проверить актуальный main.

Зафиксировать фактический release path: Cloudflare Git integration, ручной Wrangler либо внешний pipeline; ветку/триггер/команду; источник credentials; связь worker assets и backend версии; URL окружения; способ проверки revision; rollback. Отсутствие deploy-job в этом репозитории не доказывает отсутствие внешнего CD.

Не создавать конкурирующий механизм деплоя. Нет доступа к конфигурации провайдера — записать BLOCKED и точный недостающий доступ, не объявлять публикацию настроенной. В публичные документы писать только названия параметров, никогда значения паролей, токенов или cookie.

## 2. Минимальная схема проверок

PR CI: локальные browser + worker/contract tests без платных моделей. Бессодержательный дублирующий staging-gate переименовать/убрать или заменить реальной проверкой окружения, сохранив корректные обязательные checks и зависимости auto-merge.

Deployed smoke: отдельная команда и запускаемый вручную workflow; после установления release path подключить к подтверждённому завершению деплоя. Не создавать event loop и не делать deploy в рамках самого smoke. Если есть preview/staging — проверять перед promotion; если его нет, post-deploy smoke является проверкой релиза, а не фиктивным pre-merge staging gate. Не строить второй хостинг только ради названия.

Для каждого run записывать expected git SHA и фактически подтверждённую deployed revision/version. Один лишь SHA workflow не доказывает revision сайта; stale build не получает PASS. Защитить результаты от гонки параллельных выкладок. Не использовать default-success при ошибке проверки версии или состояния.

Draft PR и PR без необходимого доступа не должны автоматически уходить в production. Не ослаблять тесты, не скрывать провал через continue-on-error и не выдавать skip за пройденную приёмку.

## 3. Реальный smoke

Изолированный тестовый профиль; фиксированный тестовый проект; уникальный run marker; маленькая задача без внешних действий, с бюджетом и timeout. Не менять рабочие проекты и не останавливать чужие задачи. Любую очистку ограничить сущностями данного run; отсутствие delete API не повод удалять чужие файлы напрямую.

1. Проверить URL и revision, войти через настоящий UI и авторизацию.
2. Прочитать список сессий и проектов; открыть «+ Новая сессия» справа.
3. Выбрать тестовый проект и отправить короткую задачу через единый composer.
4. Дождаться ID и реального ответа; проверить список/detail и связь с проектом.
5. Перезагрузить страницу; открыть ту же session по постоянной ссылке; подтвердить историю и projectId.
6. Отправить короткий reply; дождаться ответа и проверить, что это та же session, а не новая запись.
7. Проверить browser errors, отсутствие повторных POST и корректное конечное состояние. Использовать проверяемые свойства ответа, не хрупкое дословное совпадение произвольного текста LLM.

Базовый smoke — два небольших обращения к реальному агенту. Файл с известным содержимым/новый проект проверять отдельным расширенным режимом по сценарию B. Полная voice/layout/error матрица остаётся в детерминированном Playwright; реальные интеграционные проверки не заменять моками под названием E2E. При отсутствии credentials результат BLOCKED/SKIPPED с причиной, а не PASS.

## Чек-лист приёмки

- [ ] Реальный release path документирован с воспроизводимыми командами/триггерами, версиями и rollback.
- [ ] Настоящий deployed smoke отделён от локальных mock/contract tests; нет дублирования тестовой логики с B.
- [ ] Есть команда и manual workflow с URL, expected revision, тестовым профилем/проектом, timeout и ограничением расходов; секреты не публикуются.
- [ ] Smoke подключён к существующему deployment path либо явно записан ручной выпускной шаг; новый CD не придуман вместо аудита.
- [ ] Проверяется фактическая deployed revision; чужой/stale build, отсутствующий агент или demo fallback не проходят.
- [ ] Реальный login → create → refresh → reply проходит; sessionId, история и проект проверены после чтения с сервера.
- [ ] Падение шага, timeout, отсутствие credentials и stale revision имеют различимые результаты; нет ложного green и бесконечного ожидания.
- [ ] Дорогие модели не вызываются на каждом PR; профиль smoke и параметры бюджета явно заданы, не подменены мок-агентом.
- [ ] Отчёт содержит URL, UTC-время, web/agent версии, test-run link, sessionId, шаги PASS/FAIL/BLOCKED и скриншоты/trace при сбое.
- [ ] Из отчёта, логов, trace и screenshots исключены credentials и чужие пользовательские данные; сроки хранения артефактов заданы.
- [ ] Локальный CI не сломан; workflow не допускает auto-merge/draft bypass и не снимает обязательные проверки случайно.
- [ ] Финальная приёмка эпика выполнена на deployed версии с A+B+C; в #35 опубликованы доказательства, оставшиеся блокеры отсутствуют.

## Порядок завершения

Сначала аудит CD и параметров окружения, затем smoke runner/CI wiring, после этого проверка на реальном тестовом окружении и итоговый отчёт. При backend-блокере вернуться к B с конкретным воспроизведением; не менять архитектуру A для обхода.

Эпик #35 закрывается отдельно после review фактических результатов. Merge документа, зелёный CI старого кода и наличие workflow без успешного deployed run не закрывают эпик.

## Работа с draft

По `CLAUDE.md` нельзя повторно push в ветку открытого PR, включая draft. После команды на разработку создать новую implementation-ветку от main с проверенными A/B и отдельный PR, связать с этим draft и #35; закрыть подготовительный draft без merge после появления замены. Не обходить hooks и не менять git policy. Актуализировать main перед началом, не интегрировать три устаревшие ветки-постановки как готовый код.
