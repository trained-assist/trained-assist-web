Эпик: https://github.com/trained-assist/trained-assist-web/issues/35
Предыдущий этап: draft A, https://github.com/trained-assist/trained-assist-web/pull/36

Статус: постановка; приложение, тесты и backend этим коммитом не изменены. Реализацию интегрировать после реализации A, а не после слияния его документа-постановки. Аудит API можно готовить заранее.

## Цель и границы

Подтвердить, что новый единый composer создаёт реальную сессию, получает корректный sessionId, открывает её после refresh и отправляет reply в ту же сессию. Выбранный проект должен сохраняться в серверных данных, а не только в UI или тексте промпта.

Рабочая область: `worker.mjs`, `test/worker-projects.mjs`, `test/worker-stop-delegation.mjs`, новые contract tests при необходимости, минимальные адаптеры API в `src/app.js`, интеграционные разделы `docs/ACCEPTANCE-TESTS.md`. Стабильность layout/controller этапа A не перепроектировать. CI/CD и автоматизация deployed smoke принадлежат C; B передаёт ему сценарий, fixtures и проверяемые ответы.

## Сначала сверка, затем исправления

Прочитать текущие реализации web и соответствующие маршруты `trained-assist-agent`; исторические PR #6, #15, #17, #30, #34 — причины прошлых ошибок, но не доказательство сегодняшнего контракта. Проверить фактическое наличие backend-зависимостей, включая stop-bearer из agent #1184, и отдельно записать статус deployed версии.

Составить компактную таблицу: browser method/path/body → worker delegation → agent handler/body → response/events → persistence → ошибки. Не придумывать поля/API по старому README и не считать HTTP 200 доказательством запуска агента.

Минимальная поверхность: auth/logout и `/web/me`, `/web/sessions`, `/web/session/:id`, `/web/files/tree`, `/web/project-create`, `/web/upload`, `/web/transcribe`, `/web/run`, `/web/reply/:id`, `/web/stop/:id`. Для файлов проверить также чтение возвращаемых ссылок и доступность содержимого агенту.

## Инварианты

- Username/profile определяется проверенной авторизацией; sessionId и принадлежность проекту не смешиваются между профилями.
- Create проходит через реального агента. Недоступность/несовместимость agent endpoint не превращается незаметно в успешное demo/echo выполнение.
- SessionId согласован между ответом/событиями запуска, списком, detail, refresh и reply. Ошибка `done` без ID не маскируется бесконечной загрузкой.
- Разрыв отображения не равен неуспеху задачи. Не повторять mutation POST для восстановления стрима. Один POST со стороны UI сам по себе не доказывает серверную идемпотентность: проверять количество созданных сессий и сообщений; отдельно фиксировать семантику неизвестного результата.
- Связь с проектом сохраняется сервером и проверяется повторным GET. Префикс `[Work in folder: ...]` сам по себе не является доказательством такой связи. Изменение wire-контракта — только согласованным paired PR.
- Успешный upload не доказывает, что файл дошёл до агента. Проверить фактическое содержимое, принадлежность профилю, частичный сбой загрузки и восстановимый draft.
- Stop должен останавливать реальную нужную задачу, а не только менять локальный badge. Дополнить использует подтверждённый lifecycle; не подменять ошибку остановки успешным restart.

## Backend-блокеры

Если ошибка в агенте, оформить отдельный paired issue/PR в `trained-assist-agent`, привести минимальное воспроизведение, контракт и тест. Записать совместимые версии и порядок выкладки. Нельзя закрывать блокер только frontend-заглушкой. Отсутствующий доступ к живому окружению помечать BLOCKED, не PASS.

Для live-проверки использовать отдельный тестовый профиль и маленькую задачу без внешних действий. Ожидаемые результаты задать проверяемо: ответ присутствует в серверной истории, sessionId стабилен, проект сохранён, файл читается. Не требовать произвольного точного текста LLM, не гонять дорогую модель на каждом локальном коммите.
